# The dashboard

A static website. Four files, no server, no build step, no framework.

```
dashboard/
  index.html      structure — the tabs, the filter bar, the panel headings
  styles.css      all the styling; every colour and font is a token at the top
  app.js          filters, charts and tables (the descriptive tabs)
  model.js        the Overturn Model and Progress tabs (Weeks 7–9)
  data.js         generated by Python — never edit this one by hand
  model_data.js   generated by Python — never edit this one by hand
```

Open `index.html` in a browser and it works. That is the whole thing.

## Running it

```bash
# refresh the data after any pipeline change
python scripts/12_export_dashboard_data.py      # descriptive tabs  -> data.js
python scripts/18_export_model_dashboard.py     # model + progress  -> model_data.js

# then just open it
open dashboard/index.html          # macOS
```

### The Overturn Model tab (Weeks 7–9)

Everything on it is read from what Weeks 8 and 9 wrote — the export fits and
re-scores nothing — except the strike-zone map, which is the **locked p(s)**
itself: `18_export_model_dashboard.py` loads `models/production/` through
`src/abs_predict.py` (hashes checked) and evaluates it on a grid over the plate
for three batter heights. Hover any spot to read the exact probability the MDP
will use. The other panels: the four model families compared on the same games
(August, or September once the test month has been opened), the reliability
diagram before and after calibration, the calibration-method table, calibration
by subgroup and by month, what the boosted model relies on (the leak check), and
the production decision in words.

The **Progress** tab is the fall plan with each finished week's result read from
its outputs. Week statuses update themselves as `models/week8/selection.json`
and `models/production/manifest.json` appear.

If you'd rather serve it (closer to how GitHub Pages behaves):

```bash
cd dashboard && python -m http.server 8000
# visit http://localhost:8000
```

## Putting it online

GitHub Pages hosts static sites free and keeps them up permanently. No account
beyond GitHub, no credit card, no cold starts.

1. Push the repo to GitHub.
2. Repo → **Settings** → **Pages**.
3. Source: **Deploy from a branch**. Branch: `main`, folder: `/ (root)`.
4. Wait about a minute. Your site is at
   `https://<your-username>.github.io/<repo-name>/dashboard/`

To get a cleaner URL, move the four files to a `docs/` folder and set the Pages
folder to `/docs` — then it's `…github.io/<repo-name>/`.

Every `git push` updates the live site. That is the deployment process.

## Why it was built this way

**Why a static site and not Plotly Dash.** Your proposal names Dash, and Dash is
a fine tool — but it's a Python *server*. Something has to be running for the page
to exist. Free hosting tiers put those servers to sleep after a few minutes idle,
so a recruiter clicking the link off your resume waits 30–60 seconds staring at a
blank page, or you pay a monthly fee forever. A static site has no server to
sleep. It loads instantly, costs nothing, and will still be there in five years.
Note the change in your Week 14 writeup as a deliberate decision with a reason —
that reads better than silently not matching the proposal.

**The Spring interactive work still fits.** This was the thing to check before
committing. The simulator doesn't need Python at request time; it needs the
*answers* Python already computed. Solve the policy in Python, export the lookup
table as JSON, and the browser reads it. Same for game replay: export the pitches
for each game. The computation stays in Python where it belongs, and the website
stays static.

**Why no React, Vue, or charting library.** You said you want to edit this
yourself. A framework means a build step, a `node_modules` folder, and a new
vocabulary between you and your own page. Every chart here is about 20 lines of
SVG you can read top to bottom. To add one: put a `<div id="c-whatever">` in the
HTML, copy the closest draw function in `app.js`, call it from `render()`. That's
the whole extension model.

**Why the data is pre-aggregated.** A full season is roughly 700,000 pitches.
Nobody is downloading that. But challenges are *rare* — about 8,000 a season —
which is small enough to ship whole. So the export does two different things:
every challenge goes out as an individual row, which is what lets you filter
them any way you like and have the page respond instantly; everything that needs
the pitch-level denominator gets counted in Python first and ships as a small
summary table. The rates stay exact because each summary cell keeps both the
numerator and the denominator.

**Why `data.js` and not `data.json`.** Browsers block `fetch()` of local files for
security reasons, so a `.json` file would work on GitHub Pages but break when you
double-click `index.html` on your laptop. A `.js` file loaded by a `<script>` tag
works in both. One less thing to debug.

**Why one filter row at the top instead of filters inside each chart.** When
every panel re-renders against the same selection, the numbers on screen always
agree with each other. Per-chart filters are how dashboards start contradicting
themselves.

**Why the colours are what they are.** The page is pink, but the three chart
colours — rose, plum and jade — were chosen so they stay distinguishable for
colour-blind readers (checked with a colour-vision simulator, in light and dark
mode, and against the white card) — roughly 1 in 12 men has some form of colour
vision deficiency, and a committee is not a controlled audience. The rule the
palette follows: one hue light-to-dark when the thing being shown is a
*quantity*, different hues when it's an *identity*. That's why the challenge
inventory bands are three shades of one pink (they're ordered: 2, 1, 0) while the
challenger roles get three different hues (they're just different people).

**Why the tables still look like box scores.** Inside their rounded cards, the
tables keep dense rows, hairline rules and right-aligned numbers in fixed-width
figures so the digits line up in columns — the convention baseball reference
sites have used for a century, and the most information per screen.

## Editing it

**Change a colour or a font.** Open `styles.css` and look at the `:root` block at
the top. Every colour and typeface in the entire site is a token there. Nothing
further down the file uses a raw colour value, which is what makes this safe —
change `--series-1` and every chart that uses it updates.

There are two blocks below it that redefine the same tokens for dark mode. If you
add a token, add it in all three places.

**Where each part of the look lives** (all in `styles.css` unless noted):

| to change… | edit |
|---|---|
| the pinks | `--accent` (links, selected tab, pressed buttons), `--accent-soft` (light pink fills), `--accent-line` (pink outlines), `--stitch` (the stitches) |
| the page and card colours | `--page` (behind everything), `--paper` (cards — also the chart background), `--card` (the soft tint in inputs and table stripes) |
| the fonts | `--font-head` (titles: Lora) and `--font-ui` (everything else: Poppins), **and** the Google Fonts `<link>` near the top of `index.html` — change both |
| how round things are | `--radius` (cards), `--radius-md` (banners, timeline rows), `--radius-sm` (inputs); tabs and chips are fully round (`border-radius: 999px`) |
| the shadow under cards | `--shadow` (set it to `none` for flat cards) |
| the baseball stitches | the block under "the stitches": the pattern is the little SVG in the `mask`; they appear under the title (`.masthead-rule`), beside section titles (`.sectionhead::after`) and above the footer (`footer::before`) — delete a selector from that list to drop the stitches there, or add `<div class="seam"></div>` in `index.html` for a stitched divider anywhere |
| the cards | `.panel` (chart cards), `.stat` (the number tiles), `.tablewrap` (tables), `.filters` (the filter bar), `.stub` (Spring tabs), `.timeline` (Progress) |
| tabs, chips, buttons | `.tab`, `.chip`, `.linkbtn` (Reset), `.theme-btn` (Dark/Light) |
| the hover box | `.tip` |
| chart colours | `--series-1/2/3` and `--seq-1…7` (see "Why the colours are what they are" — keep a replacement about as light or dark as the colour it replaces, and run it through a colour-blindness simulator such as Coblis) |
| how round the bars are | the `4` (and `3` for the histogram) passed to `barPath(…)` in `app.js` |

**Change the text.** All the headings and explanatory copy are plain text in
`index.html`. Search for the sentence you want to change and change it.

**Add a chart.**

```html
<!-- in index.html, inside a .panel -->
<div class="panel">
  <h3>Your finding stated as a sentence</h3>
  <p class="note">One or two lines of context.</p>
  <div id="c-mychart"></div>
</div>
```

```js
// in app.js, near the other draw functions
function drawMyChart(ch) {
  const counts = {};
  ch.forEach(c => { counts[c.team] = (counts[c.team] || 0) + 1; });
  const rows = Object.keys(counts).map(t => ({ label: t, value: counts[t] }));
  barsH($("#c-mychart"), rows);
}
// then add this line inside render()
drawMyChart(ch);
```

The chart helpers available to you are `barsH`, `columns`, `lineChart`,
`stackArea`, `heat` and `histogram`. Each one takes a container and an array of
rows.

**Add a tab.** Copy one of the `<button class="tab">` lines and one
`<section role="tabpanel">` block, matching the `id` and `aria-controls`
attributes. If the new tab should respond to the filter bar, add its name to the
`FILTERED_TABS` list in `app.js`.

**Write headings as findings, not labels.** "Catchers win 55% of their challenges"
tells the reader something; "Challenges by role" makes them work it out. You'll be
standing next to this during the demo — let the headings do some of the talking.

## Known limitations, stated on the page

- Opportunity denominators can't separate catcher from pitcher. An opportunity
  belongs to the *fielding side*; which of them challenged is only known after one
  does. So rates built on opportunities group the two together, and the page says
  so under the chart.
- Leverage is plate-appearance grain, not pitch grain.
- The strike zone drawn on the Zone tab is for a median-height batter. Each
  batter's real zone differs, and the distances are computed per batter — the
  rectangle is indicative, the numbers are exact.

These are in the Methods tab too. Naming your own limitations is better than
having a reviewer find them.
